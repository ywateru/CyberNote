# CyberNote UI 质量审查与改进路线

2026-11-20 · 审查基线源码修订 `4348a29acbc77d80b36f5f573e53c81958acb892` · 发布版本 `0.2.3`

本页记录本轮对桌面、手机和 Android 系统表面的审查结论、已经落地的源码改进，以及尚未完成的设备验收。目标不是把所有界面做成同一套视觉，而是让每个页面在内容预算、层级、主操作、焦点、空态和平台表面上遵循同一套产品规则。实现行为与后续建议分开标注；浏览器 fixture、Kotlin 编译和真实 Android 安装包验收是三种不同证据。

相关契约：[双端呈现](adaptive-presentation.md) · [设计规则](design-rules.md) · [设置规格](preferences.md) · [Android 快速首页](android-quick-home.md) · [主题与呈现架构](../architecture/theme-presentation.md)

## 审查结论

当前界面已有稳定的三栏工作区、单栏移动流程、五档字号、八套主题和可复用的设置/附件组件，基础并不需要推倒重建。影响“顶级产品感”的主要问题集中在五类：

1. **内容预算没有先于断点决策。** 旧实现先把窗口缩到 700px 才切换交互，却允许三栏继续压缩正文，导致正文可读宽度先失效。
2. **手机页头承载了过多平级动作。** 视图、更多、文件夹、设置和返回同时争夺横向空间，长目录名和搜索范围没有稳定位置。
3. **同一业务动作在多个区域重复。** 列表、编辑器工具栏和底部 footer 都能创建笔记，用户无法形成稳定的动作地图。
4. **状态与控件标准不完整。** 搜索焦点、设置焦点、空态、筛选空态、错误恢复和移动端行布局各自演化，缺少同一套可验收基线。
5. **Web 表面与 Android 系统栏没有同一所有者。** 页面内容使用主题表面，但状态栏/手势导航区可能仍由窗口或 `theme-color` 单独着色，形成顶部、底部色带。

## Android 顶部状态栏与底部操作区

### 观察与根因

用户提供的 Android 首页截图显示：内容区是冷灰集合背景，但顶部状态栏和底部手势区是浅粉白，形成两条不属于当前页面的“系统色带”。这不是单一页面背景问题，而是两个事实没有接上：

- Web 页面已经通过主题 token 渲染 `.notes-pane`、`.editor-header`、`.editor-tools` 等表面；
- Android 窗口在 edge-to-edge 下仍可能使用窗口背景、启动主题或 `meta[name="theme-color"]` 的旧值绘制系统栏区域。

`theme-color` 只能表达一个全局提示色，不能表达“集合页上下都是 `--grouped`、编辑页上下是 `--paper`、设置弹层顶部是白色页头而底部是灰色内容表面、格式面板打开时底部跟随格式面板”这种页面级事实。因此不能继续用单一 `theme-color` 代替系统栏投影。

以用户提供的首页截图为例，修复目标不是把两条浅粉色带换成另一种固定颜色，而是让顶部状态栏和底部手势/导航区都跟随当前 `.notes-pane` 的 `--grouped` 表面；进入编辑页、设置弹层或打开格式面板后，再按各自相邻表面重新投影。浅色表面上使用深色系统图标，深色表面上使用浅色系统图标，避免“颜色看起来接近但图标不可读”。

### 产品规则

1. **系统栏是相邻表面的延伸，不是独立装饰。** 顶部状态栏必须延续其下方页头或页面表面；底部导航/手势区必须延续其上方操作栏、集合背景或格式面板。不得出现与页面无关的固定粉白、灰色或启动页色带。
2. **上下分别取色，但各自必须连续。** 这里的“颜色一致”不是强制顶部和底部使用同一个 RGB，而是两边都不得脱离各自相邻的内容表面；同一页面上下相邻表面相同（如集合页）时必须使用同一表面色，不得出现轻微色差。集合页顶部和底部通常都取集合表面；编辑页顶部取页头表面、底部取操作栏表面；设置弹层顶部取页头表面、底部取内容表面；格式面板打开时底部取格式面板表面。只要上下相邻表面不同，分别取色就是正确行为，不能用一条全局色带抹平。
3. **颜色来自已确认主题和实际可见表面。** 先读取当前页面元素的 computed background，再回退到语义 token；不读取用户正文、图片或任意页面文字颜色。
4. **图标明暗由表面亮度决定。** 浅色表面使用深色状态/导航图标，深色表面使用浅色图标。不能只根据 `schemePreference` 猜测，因为同一主题的不同区域可能明暗不同。
5. **inset 仍只有一个所有者。** `MainActivity` 继续负责 systemBars/IME 的 WebView 容器避让；系统栏绘制只使用同一份 bars inset，不新增第二套 safe-area padding。
6. **页面切换必须重新投影。** 启动页、集合、目录、编辑、设置、格式面板、主题/明暗变化、窗口旋转和键盘出现/收起都要触发一次有界的重新计算；旧页面颜色不得残留。`public/startup.js` 在 React 之前把启动纸面投影到上下系统栏，App 接管后再按页面表面重算；React 接管前的原生回退使用日/夜纸面色，而不是窗口默认粉白色。

### 验收矩阵

- 手势导航与三键导航各一次；顶部时间/电量/信号和底部手势条或按键均清晰。

### 手机卡片结构

```text
┌──────────────────────────┐
│ 标题（最多两行）      ⋯  │
│ 摘要（最多三行）         │
│                          │
│ 日期                     │
└──────────────────────────┘
```

双列卡片使用同一行的最大高度，避免同排底边参差；单列和列表模式沿用同一 DOM，不复制标题或日期。更多入口使用 44×44px 命中区，视觉图标保持次级层级。摘要、标题和日期均可被屏幕阅读器按原顺序读取。

### 桌面画廊卡片

画廊预览不是缩小的正文阅读器，而是帮助用户辨认内容的“纸张缩略图”。因此它需要比旧实现更清晰的标题与正文，但不能把选中反馈铺满整张卡片：

- 预览卡标题 12px、正文 10px，标题最多两行，正文允许换行并裁切超出部分。
- 选中态由预览卡 2px `--focus` 描边承担；标题、日期和卡片外框不再出现黄色选择横带。
- 画廊密度仍由 `PresentationV1` 的桌面密度控制，卡片宽度、间距和列数与列表/正文预算分开。

### 桌面工具栏分组

```text
[格式 清单 表格 附件] │ [录音 标签] │ [共享] │ [更多]   搜索    设置
```

分组只改变视觉节奏和溢出顺序，不改变业务处理器、快捷键、菜单内容或权限。空间不足时仍由 `desktopToolbarLayout` 计算可见项；进入溢出的动作继续使用同一 `onClick`，并保留“编辑 / 插入 / 分享 / 更多”的菜单分隔。

### 菜单焦点与格式面板表面

菜单和格式面板是主题差异最容易暴露的两个高频组件，本轮按“状态语义”而不是“页面色值”收敛：

- **焦点不是选中。** 菜单首项可以被程序化聚焦，但视觉上不能默认铺满强调色。指针打开时不使用强调色填充；键盘移动焦点时使用共享 `--hover` 表面和 2px 内嵌 `--focus` 环；危险动作只在危险表面与危险文字之间切换。这样“聚焦置顶”不会被误读为“已经置顶”，也不会与真正的 `aria-checked` 选中态混淆。
- **表面要跨明暗同构。** 手机格式面板的底是 `--sidebar`，如果控件直接使用 `--grouped`，浅色主题下几乎看不见，深色主题下又会比面板更黑。现在分组、关闭按钮和独立引用按钮统一消费 `--format-control-surface = color-mix(in srgb, var(--ink) 8%, var(--sidebar))`，让控件在浅色下变深、深色下变浅，保持同一相对层级。
- **状态与命中区分开。** 关闭、分组和引用按钮只改变表面与前景，不改变 43–44px 命中区；格式选择仍由 `--accent` / `--accent-ink` 表示当前样式，焦点环不替代选中反馈。

### 手机页面过渡与格式面板

- **过渡下垫面必须属于目标页。** `page-in` 会把整个编辑页从右侧 12% 平移进来；如果 `.app` 仍使用集合页的 `--grouped`，动画前 240ms 会露出不属于编辑页的灰色竖带。现在 `.app.mobile.page-editor` 使用 `--paper`，浅色下与正文同白、深色下与正文同黑，过渡只表达页面移动，不制造临时色带。返回集合时仍使用 `--grouped`，与目标集合页一致。
- **格式样式标签先保证可读，再保证等距。** 旧样式行使用 `justify-content: space-between` 且所有样式项可被压缩；320px + 极大字号时五个标签的 `scrollWidth` 大于自身宽度，文字互相覆盖。现在样式行允许换行，样式项使用 `flex: 0 0 auto`；正常字号仍保持单行等距，窄屏极大字号自动分成两行，不改变“标题 / 小标题 / 副标题 / 正文 / 等宽样式”的既有命名和顺序。
- **短窗允许面板内部滚动。** 格式面板高度仍受 `48vh` 约束；320×568px + 极大字号时内容超出约 32px，面板通过既有 `overflow-y: auto` 滚动，不横向溢出，也不把编辑区压到不可用。

## 视觉语言基线

产品定位是日常写作工具，视觉层级应让正文最安静、最开阔，目录和列表在边缘组织信息。Classic 继续使用 `paper #ffffff`、`sidebar #f3f3f6`、`desktop-list #f9f9fb`、`ink #19191c`、`selection #fff1cc` 和 `action-ink #895b00`；其他主题沿同一角色映射自己的表面、文字、强调、焦点和状态色。

| 设计维度 | 顶级产品基线 |
| --- | --- |
| 字体与对齐 | 沿用平台系统字体与中文回退；标题、标签、正文、元信息使用角色化字号档；目录、标题和正文共享左侧基线，固定动作沿边缘对齐。 |
| 间距与形状 | 以 4/8/12/16/24/32px 为常用间距候选；圆角按按钮、选择容器、菜单、卡片、模态的角色分别定义；圆形只用于创建、播放、录制等明确语义。 |

真机定位过程中确认了两个独立根因，并已修复：

1. **bridge 注入晚于首轮 React effect。** 页面首次投影返回空，启动脚本又可能在 React 接管后把纸面色写回系统栏。现在 App 以有界 50ms 重试等待 `NotesSystemBars`，启动脚本在 `.app` 出现后停止投影，避免旧颜色覆盖新页面。
2. **Android 8–9 的浅色系统栏会叠加系统遮罩。** 在 API 28 上继续 edge-to-edge 时，`LIGHT_STATUS_BAR`/`LIGHT_NAVIGATION_BAR` 会让系统栏显示为白色，即使窗口颜色已经是 `#f2f2f7`。现在 `MainActivity` 在 API < 29 使用平台不透明系统栏颜色并让内容由平台 inset 布局；API 29+ 才启用 edge-to-edge 和 `EdgeSurfaceDrawable`。前端仍只负责投影相邻表面，不感知这个平台分支。

这组结果只覆盖该设备、手势导航、浅色/深色 Classic 和本轮调试包。三键导航、彩色主题、冷启动首帧、IME、横屏/分屏/旋转和发布签名包仍需单独验收。
