## 代码/配置审阅发现

### P2：未完成 HTTP 请求头的连接可占满媒体服务

位置：`src-tauri/src/attachment_media/http.rs:52`、`:62`、`:79-81`、`:89-93`。

服务接受连接时先占用 32 个共享槽；直到连接任务退出才释放。Hyper Builder 只配置 keep_alive/max_headers/max_buf_size，没有调用 `.timer(...)`。本机已安装 Hyper 源码核对表明：Builder 默认 timer 为 `Time::Empty`，即使默认 header_read_timeout=30s，`Time::check(Dur::Default(...))` 在没有 timer 时也返回 None。因此本地进程只需建立 32 个连接并不发送完整请求头，就能占满媒体连接槽；这些连接尚未取得 lease，无法由 lease 撤销 watcher 清理，唯一外层时间边界为 6 小时或服务停止。新的正常图片/音视频连接随后被直接丢弃。

建议在 Builder 配置 TokioTimer 与短的显式请求头超时，并保持完整媒体流的长连接预算；验证“未发送完请求头连接占满后，超时能归还槽并恢复有效媒体请求”。本次没有运行该场景。

### P2：Mac 附件系统操作无临时副本回收/预算

位置：`plugins/tauri-plugin-notes-ui/macos/attachments.m:57-61`、`:62-78`。

每次 copy/open/reveal/share 都创建新的 `NSTemporaryDirectory()/CyberNote Attachments/<UUID>/<name>` 并写入完整原文件，随后没有登记、回收、TTL 或磁盘配额；成功、取消分享、系统 handoff 失败均未清理。定向搜索仅在独立 native 测试脚本发现删除目录代码，产品中没有对应机制。单附件上限 100 MB，反复使用会持续留下大副本，且锁定笔记后这些主动导出的副本仍会保留。

建议制定与系统剪贴板/外部文件使用期兼容的清理策略（不可简单操作结束立即删掉，否则会破坏文件粘贴/外部打开），至少加入有限留存与清理失败处理。此项不是凭据入库问题，也不是本次仓库内发现了真实用户附件。

### 性能审阅提示：Mac 文件准备在 UI 主线程且持有 Session 锁

位置：`src-tauri/src/attachment_desktop.rs:63-69`、`:20-40`，及上述 attachments.m。

主线程回调拿到 Session 锁后调用 `prepare`：完整读取附件、Base64 编码，再由 Objective-C 解码及写入临时文件；readClipboard 同样在主线程完整读取/编码最多 100 MB。对大文件/慢盘会阻塞 UI 与同时需要 Session 锁的同步请求。授权守卫的意图明确，但建议把耗时准备放到工作线程，并在主线程系统发布前重新核验授权。没有测量实际耗时，故列为静态性能风险，不把它当作已复现的卡死。
