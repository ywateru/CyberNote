## Findings

### FIX-00-QA-01 — P2 / blocking：文档校验只允许节点名，仍接受编辑器 schema 不合法的父子结构

契约：本任务要求整个归档内容预校验，architecture 的 `import_archive` 明确“完整校验”，正式富文档由 Tiptap/ProseMirror 编辑。位置：`src-tauri/src/store/archive.rs:222` 的类型白名单与 `:287` 的无父子规则递归，只检查节点类型/JSON 值/部分属性与附件引用，没有约束内容表达式。`src/Editor.tsx:251` 使用的实际编辑器 schema 对这些结构有更严格要求。

独立复现三种文档，除文档结构外均从公开 Store API 生成的有效归档衍生。Rust `import_archive` 全部返回成功，重开 Store 后非法 document 仍在数据库中；相同依赖、扩展与结构属性生成的前端 schema 执行 `nodeFromJSON(document).check()` 全部拒绝：

| 非法文档结构 | 实际 schema 错误 |
|---|---|
| `doc → text` | `Invalid content for node doc` |
| `doc → paragraph → paragraph → text` | `Invalid content for node paragraph` |
| `doc → table → paragraph → text` | `Invalid content for node table` |

证据：`docs/verification/qa-fix-00/schema-result.json`、`schema_probe.py`、`schema-check.mjs` 及三份固化输入 `schema-fixtures/`。脚本实际调用当前 Rust Store 导入、关闭/重开读取，并调用前端已安装包的真实 schema 校验；没有 mock 结构校验，也没有推定 GUI 必然崩溃或旧笔记被破坏。

影响：不合法的富文档可以越过“完整校验”边界并提交到本地库，归档成功不再意味着文档符合实际编辑器可接受的结构。本轮原三项修复及事务恢复已通过，但内容校验契约仍不满足。

要求：在文件发布与数据库修改前拒绝与当前 schema 不合的文档父子结构，覆盖 root/block/inline、列表/任务、表格行/单元格及原子节点等实际内容规则，同时保持有效文档兼容。新增真实坏归档拒绝测试须确认旧 workspace/设置/附件/源归档完全不变；独立重跑上述三份 fixture，并保持此次已通过的事务与恢复回归。
