卡片顺序确实不同，已由父任务安排修复。本次测量不支持随后大幅重排卡片网格：仅按截图宽度换算的示意数值，未选中卡片尺寸、列距、行距及面板内标题位置均较接近。下一轮应先统一选中空白纸张，再复验**选框圆角、说明文字宽度和完整交互**，不能以几项小差异代替整页通过。

## 状态、顺序与面板边界

原版选中**空白纸张**，当前 clone 选中**大网格**，两者选框不能直接当同状态像素比较。顺序按从上到下、每行从左到右目视关联，含右侧空位：

|行|原版|当前 clone|
|---|---|---|
|1|空白 / 空位|空白 / 空位|
|2|密横线 / 中横线|密横线 / 密网格|
|3|疏横线 / 密网格|中横线 / 中网格|
|4|中网格 / 大网格|疏横线 / 大网格|

图像坐标均为原尺寸解码像素，左上原点，bbox `[x0,y0,x1,y1)`。边界由目视结合稳定RGB条带判断，不是运行时测得的系统inset或控件frame：

|区域|当前 Android clone|原录屏帧|
|---|---|---|
|顶部状态区|`y[0,83)`，可见Android时间/LTE/电池|`y[0,26)`基本黑色状态背景，时钟/状态图标在内；26起进入边缘过渡|

|面板中心稳定背景起点|y138|y32；y31仍为边缘过渡|
|左边缘成为稳定面板背景|y181|y41|
|面板底部可见范围|至y2148|至帧底y480，没有可分离的底部系统导航条|
|底部系统导航区|`[2148,2280)`，132高，Android三键可见|此帧未显示独立同类区域，不推断不存在安全区|

两张宽高比分别约0.47368与0.46667。顶部状态条约占各自高度3.64%与5.42%，clone底部导航另占5.79%。因此直接把全页y差用于调整应用网格会混入系统栏与可用viewport差。

## 圆角、颜色与下一轮建议

当前clone金色外框顶行即覆盖全x范围`[598,965)`；原选中空白框顶两行仅`[26,100)`，到y116才扩展为`[24,102)`。这提示当前clone选框外缘更方，值得在**同选中plain**后优先核对。非选中白卡片顶边也有圆角，但原帧只有约1–2行过渡，clone约11行达到满宽，低分辨率/压缩无法给出可信原生圆角半径。不能将这个代理数直接换成CSS radius。

有限色样：原版平面板ROI `[105,120,119,170)` 主色`(242,241,248)`；clone `[510,570,570,790)` 全为`(242,242,247)`。空白内部原版`(255,254,255)`、clone`(255,255,255)`。这些是编码RGB，无色彩管理校准。小帧文字和金色边界已经严重混合抗锯齿/视频色偏；原版说明筛选墨迹多为约186–192，clone主体为138，但不能据此推断原始字体颜色或直接调灰。现有证据优先级不足以微调背景的1个RGB分量。

下一轮建议：

1. 修复顺序后，以两边都选中plain、相同浅色状态复抓，保留native原图和实际构建身份。核对7张卡片全序、选中/切换/保存/重开状态以及纸张实际效果，整页仍未通过。
2. 记录实际应用viewport与系统栏边界，按面板内部几何比较。若列距、卡片宽高和行距继续保持当前量级，不必为全页y差重排grid；优先量出与原版同状态后的卡片边界/圆角/选框外扩。
3. 说明文字保留全文与墨迹bbox/阈值敏感性，核对是否同一文案、字号和字体度量；当前宽差值得复验，不能因为标题位置接近而忽略。再考虑精调字重、灰度和说明到首卡间距。
4. 以更清晰的原始参考确认选框是否沿圆角、是否含内/外扩及阴影。当前原帧不足以支持“radius差1px”这类精确修复，也不足以宣布整个面板像素一致。
