# 智能文件夹交付拆分 07：共享能力、所有权与真实 UI

2026-11-04；源码基线 `48b651df7644d27dd0b699273f0a09e79f97723d`。本轮只读源码并新增本文件，没有修改产品、共享接口、schema、既有证据或 index，没有运行测试、构建、GUI 或设备命令。前一轮完整风险分析见 [implementation-readiness03](smart-folder-implementation-readiness03.md)；下文只列当前接入点、不能拆开的修改和有区分力的验收。所有字段名、动作名、版本号仍是待 root 批准的候选，不能把本文当成已授权实现。

**交付单位应是一条贯通 SQLite → Session → bridge → Mac/Android 真实导航的功能链。** 当前产品没有 smart 实体；先增加一个图标、前端常量查询或预览分支不能构成接入。建议按 D（数据）、O（所有权）、U（真实 UI）串行交付，前一批形成可复用能力，最后一批才对用户开放入口。原版引用生命周期由 root 补证；在该政策和最小共享契约定稿前保持现有接口。

## 2. 实施拆分与各批完成条件

### D：数据、后端能力和归档

**一起改：** `src/types.ts`；`store.rs` 的 Folder、open、读写、workspace、action 和物理能力判断；`store/archive.rs` 的版本、图校验、映射、export/import；对应 Store/归档测试。可新增智能规则模块，避免把规则枚举散落在动作和导入中。需要时新增数据库迁移文件，不必为动态成员新增成员快照表。

1. 按批准契约实现严格实体分支和有界规则校验，Rust 为最终权威；拒绝未知 kind/query version/枚举、非法字段组合、无效引用和空集，保留旧普通目录的合法形状。导航 `all` 不可成为 Folder 实体。持久化定义而非结果成员，名称即时由稳定 ID 解析。
2. 实现定义创建、编辑/改名、删除和持久化读取。编辑及删除按批准的定义 revision 做 CAS；失败不更改定义或成员笔记。名称与规则是否共用 revision 必须先定，不能留下另一个不校验的 rename 入口。
3. 所有写入笔记归属和 parent 的路径共同使用能力校验，包括恢复的旧 owner 与冲突副本的继承 owner。智能定义不能拥有笔记、充当物理父目录或移动目标。读取/归档也要发现非法所有权，不能只在新建时拦截。
4. 实现唯一的查询语义和一致的结果投影契约，明确结果全集、锁定元数据和直接/递归关系。若首批选 pinned/folder，只使用公开元数据，不解密正文建立索引；查询计数与列表不得走不同条件。
5. 引用删除按 root 批准政策原子处理，覆盖 include/exclude 的全部 ID、当前不匹配的分支和被删物理子树。智能删除只删定义。物理改名/移动仍保留 ID；不因改名把规则改成文字匹配。
6. 活库建立实际版本迁移/未来版本拒绝；归档 1/2 保留原义，2 已包含录音日期，新增智能格式版本另行批准。导入重映射所有自定义实体 ID、规则中的目录 ID、parent、笔记 owner/original owner、selectedFolder，并在合并图上复验。保留 `archive.rs:623` 的事务、文件发布和独立 journal 恢复边界；journal version 1 不是归档版本。

**有区分力的完成证据：** 实际临时 SQLite 创建定义→关闭→重开→相同成员；同一数据集同时区分 AND/OR、多 token 并集、A 与 A1、已删除/锁定笔记；直达 Store 的 create/move/restore/conflict-copy/parent 不能把笔记放入 smart；所有拒绝都比较完整 workspace 与文件字节不变。归档 1、含 recordedAt 的 2、新格式分别导入；同一新归档连续导入两次制造 ID 冲突，证明每份规则只引用各自副本，旧本地定义不被替换。非法规则、未来版本与故障注入均不留下半迁移/半导入。

### O：访问、通知和保存所有权

**一起改：** `session.rs`、`lib.rs`；`src/bridge.ts`、`src/types.ts` 的通知契约；`App.tsx` 的同步/水合和保存边界；必要的新元数据顺序模块。复用 `access-client.ts`、`save-queue.ts`、`save-revisions.ts` 的现有职责，不把定义版本塞入访问 token。

1. 在真实 Session 内执行定义 CAS；为定义 CRUD 和影响成员的已成功动作发布独立元数据变更通知。会话身份、单调序号、响应与通知顺序及重启行为须同契约落地，覆盖 pinned、folder move、note create/delete/restore、物理引用处理和 archive import，不能只通知 smart CRUD。
2. 接收端丢弃旧快照/旧查询响应，但仍处理其合法 note 保存 ACK。当前 `access-client.ts:38` 的保存分支只确认权限，不发布回包正文；当前 `App.tsx:871/875` 只在真实 ACK 后推进 revision/清对应 pending。新顺序机制必须保留这些行为，不能用“忽略旧 workspace”吞掉保存确认。
3. 定义/成员变化不递增匹配笔记的 note epoch，不撤 key、不清 Undo；真实 lock/delete/purge/import 仍优先走现有 prepare→排空→ACK→commit/abort。`session.rs:240` 的窗口和 note 所有权检查、`:248` 的已登记保存范围不可放宽。定义删除不凭空生成对成员笔记的访问屏障。
4. 结果离开当前视图、智能定义被别窗删除或编辑、搜索取消时，分别保留来源上下文、结果选择和实际 Editor owner；未确认文档继续归原 note。需要切换时按真实 flush/ACK 决定下一步，失败保留 pending、错误及可恢复的编辑器，不把结果首项当保存目标。

**有区分力的完成证据：** 两个真实 Session 窗口同时编辑同定义，旧 revision 写入及删除失败且新定义保持；延迟旧 workspace/旧查询回包经过 bridge 和水合后不能恢复已删定义或旧成员。窗口 A 有 pending 文档，窗口 B 改定义使其离开结果，A 的保存依旧落入原 note 且 Undo 保留。相同场景叠加真实锁定屏障，登记保存须排空，失败 ACK/丢窗/超时须 abort；旧 access 回包不得恢复正文。只做 reducer 模型或 Mutex 单线程成功不算此批通过。

### U：前端真实 UI、导航和原版对照

**一起改：** `App.tsx` 的侧栏/文件夹页、菜单、创建/编辑规则面板、`listed`/count/选择投影、保存后导航、移动候选；必要的共享导航/查询投影模块、样式、原生菜单/工具栏接线。Mac 与 Android 使用同一持久化定义和能力判断，平台布局按各自原版证据实现。

1. 只有 D/O 能力通过后开放真实创建、编辑、取消、保存、删除入口。表单草稿与已保存定义分开；取消不提交，保存等待真实成功，CAS 冲突不假关闭并覆盖新定义。不得显示一个能保存但后端不支持的规则类型。
2. `App.tsx:542` 的列表、`:2061` 的计数、`:1392` 的进入选择共同消费同一查询投影；排序/分组沿现有设置。`chooseFolder` 不能继续只以 `note.folderId === smartId` 找首篇；`createNote` 不能把 smartId 传为 owner；移动列表不能继续只排 trash。
3. 结果中创建、置顶、取消置顶、移动、删除、锁定/解锁、搜索进入/取消，以及最后一篇离开结果后的选择，各自使用 root 批准的动作表。已知有限原版样本不能推广为全部动作导航；新建转默认“备忘录”和搜索取消恢复智能上下文要与现有停车路径一起实现。
4. 侧栏/手机文件夹行使用真实智能图标与数量；规则面板的初始行、AND/OR、目录 token、禁用项和删除确认逐项对照原版。原版默认标签规则与候选首批 pinned/folder 的差异须先由 root 决定如何交付；不能把默认规则悄悄替换为置顶并声称一致。原版未证的手机画面不从 Mac 外推。
5. 智能定义不出现在物理移动/父目录候选；编辑规则中的候选与 Rust 能力同步。另窗删当前定义或引用目录后的 fallback 与旧草稿失效一致，冷启和归档恢复后的选择也走相同有效性检查。

**有区分力的完成证据：** 真实 App 从入口新建并保存、进出/冷启仍有同一规则和成员；取消编辑前后 SQLite 定义不变；修改条件同时改变列表和侧栏数量；结果清零期间保留原 note 的保存和 Undo。Mac 与 Android 各自产出同数据、同操作的原版/克隆截图与交互记录，覆盖规则面板、目录 token、菜单、空结果、取消搜索、创建去向、移动候选和删除。先以源码/自动化查因，再按准确输入冻结构建并做有限设备验收，不能把浏览器预览、纯函数或截图静态通过等同像素及交互全通过。
