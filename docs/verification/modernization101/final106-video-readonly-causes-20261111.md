## Strongest concrete candidate for tail: expired HTTP lease remains a live frontend source

Production `src-tauri/src/attachment_media/runtime.rs:54` gives MediaCore a **30-minute idle TTL**. `http.rs` runs an expiry sweep every15s. `mod.rs:278` checks elapsed time before updating `last_used`; `expire()` at483 removes/revokes idle leases. `http.rs` turns a missing/expired lease into denied404 before opening a stream. Fresh HTTP lease checks and each demand-polled block refresh activity; **playing/paused JS state is not a keepalive**.

The tail record has a material timing boundary:

If the96s video's last HTTP read completed near its initial playback, a later seek needing an uncached byte range would use an expired capability. Current frontend sources have no expiry notification or renewal timer: `attachment-source-pool.ts` keeps loaded entries until cancellation/invalidation/subscriber disposal; `use-attachment-media.ts` only reacquires on explicit dependency changes. The `<video controls autoPlay>` in `Editor.tsx:192` has no native media error/stall handler that renews an authorized source. Backend expiry itself does not send the loaded source an invalidation event. A still-mounted video, cached duration and retained last frame can therefore coexist with an unusable URL. This closely fits **a candidate**, not observed network causality.

Limits: live12 did not record last read time, HTTP404, lease ID/expiry, buffered ranges, readyState/networkState/media error, or play Promise result. A30min interval alone does not prove expiry: subsequent HTTP reads could renew it, or all required bytes could already be buffered. Faststart initial fresh-lease timestamp was not persisted, so this specific timing argument cannot be assigned to live11. Menu Play did change the control toPause/00:48, but did not prove decoding or clock advancement. Its two immediate images are only0.146s apart; final Pause about17m48.6s later was still48s/frame83.333.

Existing source-level test contract already covers backend expiry: `tests.rs:465 media_lease_idle_expiry_and_shutdown` configures20ms TTL, sleeps30ms, then asserts GET404 and shutdown. It was **read, not rerun** this task. It does not assert a paused/cached WebView's later Range request or frontend error/recovery. The expected denied status is404, **not403**. No need to rebuild merely to reprove this existing backend behavior.

The authorization event pathway is distinct: `runtime.rs:167 event` handles notes-access/notes-sync prepare by suspending authority and revoking selected owners, plus metadata invalidation/reconcile; App forwards those real events to frontend pool revoke/invalidate. The HTTP periodic `expire()` path only cancels/removes core leases; it does not emit such a frontend event. AttachmentSourceGrant has no expiry field. Thus authorized frontend source ownership can outlast the backend capability without a renderer signal. This establishes a source boundary, not that expiry actually happened in live12.

Smallest future discriminating **frontend** check, if separately authorized: reuse the production core's injectable short TTL with an isolated small valid seekable video and the actual production MediaView. Keep the exact same authorized visible owner, mounted element and pending position; allow playback/paused buffered data, let its HTTP capability expire, then make one uncached Range demand. Record404 plus media error/state, rather than just another backend GET assertion. Verify error becomes visible, one explicit reacquire action obtains a fresh capability, and real currentTime/frame progression resumes at the same intended position after metadata/seekable validation. Separate that from optional automatic recovery; do not assume native media always emits `error` promptly for stalled network. A bounded stall indication may need a separately defined product contract. If owner/access/navigation changes before reacquisition or late receipt, no source may publish or auto-play. Do not disable expiry, retain every playing lease forever, or use an expired URL as authorization.

## Suggested first product fix, after causal validation

Prioritize a **visible video load/playback error with explicit retry**, rather than changing lease retention globally. The source gap is definite: MediaView video has no onError/loading-stall presentation; its displayed inline error comes from source-acquire failure only. A later HTTP capability failure can therefore leave controls/last frame without actionable failure UI. The existing hook has an authorized retry/version path, but the video does not connect actual media failure to it. Native-menu play rejection already reaches the app error path; play Promise resolution alone still does not prove progressing media.

A narrowly defined retry should request a new source under current permission and exact attachment/owner; preserve desired time only for that same live owner and after new metadata confirms a valid seekable range. Source old/new cleanup must retain pause/remove-src/load, release and late-grant disposal; navigation, editor destruction, note lock, access/sync prepare and window replacement must remain immediate stop/revoke boundaries. An offscreen/unmounted request must not resurrect playback. No unconditional heartbeat or authorization bypass is justified. This is a suggested fix scope, not an implemented or tested change, and does not certify TTL as the native root cause.
