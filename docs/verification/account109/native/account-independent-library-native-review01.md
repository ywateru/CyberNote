## Blocking finding

**P1 — protect renderer-only work before the destructive Session authority reset.** At the integrated ref, `src-tauri/src/session/synchronization.rs:240–251` checks native pending operations, registered save intents and quiet operations only. `adapter.rs:613–632` proceeds directly from that check through media verification and Store adoption; there is no all-window probe/freeze/drain acknowledgement. `sync_finish_workspace_adoption` then replaces the session ID and constructs a commit event targeting every note (`session/synchronization.rs:257–269`). The existing `App.tsx:1843–1853` access handler calls `clearSensitive`, whose lines 1657–1661 clear tag composition and lines 1679–1681 destroy the affected Editor instances.

A second real note window can be composing input or retaining editor-only work while the account window enables synchronization. Such work is represented in the existing renderer quiet snapshot (`App.tsx:1033–1049`) but need not have a native save intent. The new native preflight therefore succeeds and the later access event can destroy that editor without a successful preservation acknowledgement. This also affects first activation, which rotates Store/Session identity. A registered intent test alone does not cover this path; save failures may also consume their native intent while the renderer retains pending work (`session.rs:343`, `App.tsx:1289` onward).

Required correction: either preserve independent local editor authority and avoid this destructive access event while separately fencing old sync backends/plans/media, or establish a bounded, all-live-window adoption barrier before invalidation, including composition, pending/failed saves and media/editor operations. For the barrier approach, obtain preservation acknowledgements and fence new admission through final commit/abort; any missing or blocked participant must leave adoption blocked, with the account logged in and local editing recoverable. Retain native transaction-time revalidation. A single account-window button guard does not protect other windows or native command callers.

## Additional recovery finding

**P2 — retain/replay the post-commit access notification after an emit failure.** `adapter.rs:629–635` commits Store adoption and rotates Session authority before the fallible `host.emit`. If that emit fails, the pending marker remains and enable is reset by the account task, but the new DB identity is already durable. On the next explicit enable, same workspace/device takes the Store no-op path (`store/synchronization/schema.rs:194–197`); unchanged Store instance makes `sync_finish_workspace_adoption` return `None`. Activation can then complete and clear the marker without ever notifying a window that missed the first event. Its old native save/access tokens are invalid. Provide a recoverable pending-notification/authority synchronization path, including partial delivery to multiple windows; do not undo a committed DB by pretending the first attempt never happened.
