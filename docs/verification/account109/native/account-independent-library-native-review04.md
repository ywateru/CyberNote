## Remaining P2 — preserve post-commit completion across notification failure

At `src-tauri/src/sync/adapter.rs:772–785`, Store adoption commits, `committed` becomes true, the old quiet operation is released internally, and Session authority rotates **before** the fallible `notes-sync` release and `notes-access` emissions. `session/synchronization.rs:353–366` changes the Session id and replaces the entire quiet state, deleting the just-recorded terminal receipt. Adapter cleanup at lines 789–800 runs only before commit, so neither post-commit emission failure retains a completion notification for retry.

The new renderer barrier makes the lost-release branch concrete:

1. All real windows ACK prepare and retain their quiet edit gates.
2. Store commits; Session rotates and forgets the old terminal.
3. The release emission at adapter line 782 fails or reaches only some participants; access emission is skipped. A missed window still has the old Session/token and a frozen lease.
4. Its existing 5.5-second renderer timer requests cancellation; it deliberately cannot unfreeze without a native terminal (`src/network-sync.ts:236–240,278–305`). Adapter `reply` checks the current window token before looking up the terminal (`adapter.rs:1175–1181`), and Session id has changed. Even retaining a terminal without a narrowly valid retired-operation receipt path would therefore be insufficient.
5. Explicit enable retry finds the DB already on the requested workspace/device and immediately returns from `adopt_account_store` (`adapter.rs:702–705`). Activation can clear the adoption marker (`670–671`) without replaying the old release or access snapshot. New-Session probes do not repair a window which still recognizes the old Session. Restart can bootstrap a fresh window, but the current explicit retry is not the requested completion recovery path.

If release succeeds and only access emission fails, the renderer commit callback's trusted metadata read may recover that window. That partial defense does not close the failed/missed release branch or establish recovery for every participant. No data loss is inferred from this failure; the proven issue is stale/frozen window authority after a committed migration and an apparently successful later activation.

Required correction: retain a pending adoption completion/authority publication until affected live windows can obtain the committed terminal and trusted new snapshot, including partial delivery. Retry of an already-adopted pair must reconcile that completion before clearing its pending state. A narrowly scoped retained-operation receipt/resynchronization path must validate the original participant and operation without accepting retired tokens for ordinary writes or new operations. Do not roll back a committed DB, weaken normal authority checks, or let a renderer timer guess abort.

Minimum meaningful regression: inject failure on the first post-commit release emission, retry the same workspace/device, and establish exact business/media preservation plus recovery of the original window(s)' freeze and authority. Include partial two-window delivery and access-only failure. Existing always-successful AdoptionWindows fixtures and passing Store SQL/Session handshake fixtures do not cover this branch.

## Follow-up clarification — exact P1 closure and minimum P2 strategy

Rechecked the existing renderer consumers together with the native barrier. Main adapter/enrollment commit `3603b187` is byte-equivalent to author `487af516` for those files; Session `8cb6456a` is equivalent to author `3ef56755`, and Session `ff8d0628` to author `213b1a5a`. The adoption-specific all-note target/ACK gate plus final native checks close review01's original **pre-commit renderer-preservation P1**. The renderer protects composition and media operations, flushes pending/failed saves before ACK and holds a document/authority-checked freeze lease. This closure is static; no real window execution is claimed. Post-commit completion remains a distinct, unclosed failure, so complete-native approval remains **BLOCK**.

The minimum correct notification strategy must meet all of these conditions; a queue alone is insufficient:

1. **Capture one stable committed completion before fallible delivery.** Keep the original operation/old Session, new Session and Store instance/pair, original participant window incarnations, and the release + new-authority access payloads together. Preserve this record across Session quiet reset and explicit retries; mint no second Session or fake abort for the already committed DB. The existing disk marker may retain restart pause semantics; an in-process completion record need not replay an obsolete process Session into freshly bootstrapped windows after process exit.
2. **Retry completion before treating the same pair as a no-op.** Deliver release then access to each unresolved participant, with per-participant progress or safe full-pair retransmission. Do not clear the pending completion/adoption marker merely because the DB pair now matches or one broadcast returned success. A resolved/closed original window must not be confused with a new window reusing its label. New adoption must not overwrite an unresolved record or replay its stale authority after another Store replacement.
3. **Make retransmission idempotent before destructive renderer work.** Main `bridge.ts:52–61` currently invalidates AccessGate for every notes-access event, and `App.tsx:1843–1853` then clears editors/documents. Blind global replay could destroy new editor-only work in a window which already recovered. Use a unique completion identity and per-window applied/in-flight state (or an equivalent targeted acknowledged protocol). Coalesce concurrent duplicates; never run the destructive transition twice or regress a newer authority. A successful completion means that window has adopted the trusted new snapshot, not just that native emit returned. Retrying one missed participant must leave the recovered window's subsequent unsaved edit untouched.
4. **Preserve a safe recovery receipt.** A missed old-Session release must be recoverable without accepting retired write authority. A narrowly scoped receipt keyed to the original operation and original participant incarnation may report only the committed outcome and lead to trusted new-state synchronization. Do not globally bypass Session token checks or return commit for arbitrary old operations. Account cancellation/logout may stop transport, but cannot change an already committed completion into abort or silently forget its frozen windows.
5. **Verify both halves and partial delivery.** Inject release failure before any delivery, release/access failure after one of two windows advances, access-only failure, and a lost acknowledgement followed by duplicate replay. Assert unchanged Store identity after retry, no re-adoption, exact saved bodies/media retained, old normal write tokens rejected, missed windows recovered, and already-recovered windows' new unsaved work preserved. Also cover confirmed closed/replaced window incarnations and cancellation after DB commit. No test run is claimed here.

These are acceptance conditions for the author's smallest implementation, not a request to add a general notification system or weaken authentication. The eventual complete-native verdict will review the integrated P2 code and its focused evidence together with this already-reviewed barrier; it will not leave the residual finding outside scope.
