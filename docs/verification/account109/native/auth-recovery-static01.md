# Auth recovery: preliminary static review

2026-11-13. Source-only inspection at main `5a42891787272b0448c39d6b28f4063d0d18382f`; preliminary guidance, not approval of an implementation. No tests, builds, device, App, browser, credentials or network used. Huygens's design and eventual exact native/UI commit, plus Socrates's separate runner commit, still need review.

1. **Classification alone leaves a recovery gap.** `AccountSettings.tsx:176` chooses `status` for a network-error profile whose enabled flag is false. Native `Command::Status` at `src-tauri/src/account/mod.rs:391` is read-only; `SyncNow` at line 493 requires enabled. Startup `restore` can fail before `bind` restores the persisted enabled flag. Therefore a partial-profile startup transport failure has no effective in-place retry through that UI button. This is a source-derived path, not evidence of the actual relogin01 cause.
2. **Keep transport retry distinct from reauthorization.** A minimal explicit retry should rerun refresh/restore and the existing strict `bind` path using the retained grant, inside the current lifecycle/generation ownership. It must not logout, open the browser, replace binding, create a new identity, or set enabled true. After successful bind, honor the persisted enabled setting: paused remains paused and uses the existing merge confirmation if the user enables it; previously enabled recovery may restart the existing account network. Keep polling `Status` read-only and avoid an automatic retry loop.
3. **Do not route a generic error into replacement authorization.** `authorization_mode` at lines 695–700 currently permits any `Phase::Error` to enter reauthorization, and `login` at lines 533–537 revokes the existing grant before starting a browser transaction. The UI's current regex routes authentication codes to SignIn. A proposed fix should offer that path only for a reliably classified recovery action; unknown/transport errors must retain their initial cause and grant. Preserve cleanup-required, ownership, configuration, storage and protocol fences instead of treating all errors as transport or authorization rejection. Do not infer server rejection from the older binary's flattened `RefreshFailed`.
4. **Preserve existing binding and cancellation checks.** `bind` verifies pinned issuer, original issuer/subject, coordinator profile, workspace ownership and complete device binding before replacing status. Reuse it. New retry work must serialize with restore/sign-in/sign-out/exit; cancellation/generation changes must prevent late status or network resurrection. UI must not turn an old failed SignIn into another authorization while the native state is already authorizing or healthy. Pending authorizing profiles may be partial; terminal username/subject/health checks stay strict in the runner.

Small focused coverage should distinguish request transport from server rejection without raw upstream leakage, show one explicit transport retry retaining grant and binding, cover initially paused and enabled cases, and reject late success after cancellation/logout or changed subject/workspace. UI checks should prove the intended retry command is sent rather than a no-op status or SignIn, and that enable still requires confirmation. These are review targets for the proposed change, not instructions to broaden the current implementation without an agreed design.

## Reauthorization failure after successful old-owner cleanup

Additional source-only inspection of Huygens worktree HEAD `5aef7718800275d6d6c37326f90bb345616094b4` plus its uncommitted native/UI recovery changes; this is WIP feedback, not an exact-commit verdict. The user-proposed path is reachable:

- A classified refresh rejection admits explicit replacement SignIn. `login` successfully calls `auth.logout`, whose success clears the old grant, then `begin_authorization` discovery or browser opening can fail. `fail` retains or repopulates the bound subject-only profile, so a profile is not proof of a remaining session.
- Network recovery then calls retained `auth.restore`; with no grant it returns `None`, mapped by the runtime to `identitySession`. Current WIP `authorization_mode` permits an initial retry only with no profile, and the UI selector has the same restriction. A subject-only `identitySession` error consequently cannot retry SignIn, and its generic network wording is misleading.
- This does not remove every exit: the actual UI still renders the existing SignOut action for that profile. Explicit confirmed SignOut stops the network; logout with no grant succeeds without an upstream request, clears status and disables the binding while retaining its ownership. Subsequent SignIn still goes through strict original binding checks.

The smallest safe resolution is to explain that this authorization attempt did not complete and explicitly guide the user to the existing SignOut confirmation, then login with the original account. Preserve cleanup-required failures and the old ownership binding. No automatic cleanup of an unknown grant is needed. Cover the actual sequence from successful logout through failed begin/browser, restore None and explicit SignOut to a permitted new authorization; selector-only tests do not establish this path.

An alternative is a native-proven absent-session, begin-only retry with matching UI action and strict binding. It must not infer absence from a stale profile or a broad `NoSession` label: `NoSession` can also represent an unusable retained grant, while `cleanup_required` must keep priority. `begin_authorization` already rejects any retained grant as Busy. Also note that callback-listener setup occurs **before** replacement logout, so callback-listener failure does not establish that cleanup succeeded or the session disappeared. These constraints were sent directly to Huygens for the final implementation choice.
