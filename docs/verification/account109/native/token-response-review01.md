## Coverage and findings

- The rejection matrix actually exercises code exchange, refresh with an ID token and refresh without an ID token. Each path tests non-Bearer type, empty access token, missing expiry, zero expiry and a present scope without connect: 15 cases for four field categories. The real AuthClient/fixture response path is used; rejected access is unavailable, and refresh rotation remains quarantined under its latest cleanup owner. Initial rejection uses the existing successful revocation fixture. No test claims to exercise a public issuer or a real browser.
- Nine scope-positive cases accept absent scope, connect alone and the usual OIDC-plus-connect set across those paths. This agrees with current validation: present scope must include connect, but omission is allowed. Missing required JSON fields can fail parsing earlier; the empty access-token case must not be described as covering an omitted token field.
- Two replacement sequences verify retained grant blocks begin before cleanup, failed revoke retains/quarantines the owner, successful logout permits begin, and cached begin adds neither a refresh nor a code request. The observed fixture sequence is discovery → JWKS → code → refresh → revoke. This establishes AuthClient request ordering in that fixture, not actual Tauri/browser execution.
- Independent Runtime source tracing agrees with the investigation: startup restore owns the lifecycle mutex; accepted explicit SignIn uses the same owner, stops the old network, advances generation and spawns login. Login obtains the cached auth owner, binds the callback listener, settles replacement logout, begins authorization, invokes the opener and waits for callback before code exchange. It does not run an implicit pre-login restore. A later strict-bind access-token request with minimum validity 60 seconds can refresh an otherwise positive short-lived code grant. Thus the retained responseMetadata reason does not distinguish code response from a later refresh.
- The four response-envelope checks precede ID-token verification, or prior-identity reuse on refresh without ID token. Discovery failures have a different outward mapping. The investigation correctly limits the observed rejection to a successfully parsed envelope; it does not establish which field failed, provider fault, scope incompatibility or absence of a browser round trip.
- Browser-tab count and short run duration do not prove that the opener was never invoked. The document explicitly preserves transient/reused-tab possibilities. This reviewer did not inspect browser/runtime state or reread the live result.
