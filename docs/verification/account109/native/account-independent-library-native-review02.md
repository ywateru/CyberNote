## P1 — retained-session startup failure loses the connection-recovery route

`account/mod.rs:85–101` loads the binding while leaving Status at its default: no profile and enabled=false. `restore` (170–210) sets the profile and enabled intent only after `bind` completes its access-token/profile request and validation (214–258). The new `fail` (141–148) no longer supplies the binding fallback profile. This correctly avoids reviving stale A during a failed fresh B login, but leaves retained-session startup errors indistinguishable from a failed first login in the public status.

| Failure point at a normal retained restart | Result at the reviewed source |
| --- | --- |
| `auth.restore` refresh transport/discovery failure, including refresh HTTP 429/5xx | Grant retained; no profile; status enabled=false even if binding intent remains true. UI `accountConnectionRetry` chooses signIn for identityProvider network errors. |
| `bind` access-token or coordinator profile transport failure / timeout / HTTP 429/5xx | Existing bound grant is deliberately not logged out; still no profile. CoordinatorProfile network errors likewise select signIn. |
| Provider network error with providerReason=network and no profile | UI returns status instead of syncNow; a main login attempt is rejected by native authorization_mode as Busy. The provider-stage branch is a separate selector gap, not a claim that the direct auth.restore call emits SDK provider errors. |
| Failure after successful bind while starting transport | Profile and persisted enabled intent have already been restored; the existing profile-based network retry path still applies. This is not the same regression. |
| Confirmed refresh rejection / quarantined cleanup / configuration or invalid response | Must retain their finite distinctions. They are not evidence that ordinary offline recovery should revoke authorization; no blanket retry or automatic reauthorization is proposed. |

The erroneous signIn path is worse than a misleading button. Native authorization_mode allows begin-only for profile-less identityProvider/coordinatorProfile errors, then SignIn calls `pause_for_account` and **persists enabled=false before beginning authorization** (`mod.rs:431–446`). AuthClient still owns the grant and returns Busy (`crates/account-auth/src/lib.rs:157–168`); Runtime maps that Busy to CleanupRequired (`mod.rs`, login begin_authorization error mapping). An explicit “retry connection” intent therefore becomes a cleanup demand and can permanently change an existing enabled binding to paused without establishing grant rejection.

Native `SyncNow` already has a bound-network-error route (`mod.rs:575–590`, `network_recovery:926–935`) through `recovery::run`: restore the retained grant, strictly bind, and start only if its persisted enabled intent is true. The UI currently requires a profile to select that route (`src/account-client.ts:74–81`), making it inaccessible for this startup failure. The main UI also treats profile-less state as signed out and offers login (`AccountSettings.tsx:164–165,199–205`). The helper tests instantiate the recovery Host directly and do not establish that this real startup-to-UI path remains reachable.

Required correction: represent retained-session recovery explicitly, scoped to the current lifecycle/generation and validated local session state, separately from a failed fresh authorization. Do not restore the unconditional old-binding-as-current-profile fallback. Expose an explicit action that can reuse the retained grant before a new profile is available, leave both persisted enabled=true and enabled=false unchanged during a failed retry, and preserve strict identity/workspace/profile validation before any network resumes. A→B failure must not revive A's profile or enabled policy. Only actual refresh rejection or required revocation cleanup may lead to the corresponding explicit reauthorization/cleanup action.

## P2 — persistent non-conflict adoption blockers lack a supported recovery path

At this exact source, the safe refusal can become a persistent **enable** dead end through supported commands; login and local editing can still succeed. Store preflight rejects any inbox and missing/mismatched projections (`store/synchronization/schema.rs:86–133`). Such state can have conflicts=0; a single unprojected head may also have pending=0. Conflicts alone therefore do not describe all blocked states.

Login pauses the manual service, sets active=false and aborts the current quiet operation. `adapter.rs:1045–1140` continues ticking existing quiet operations while inactive, but starts a new generic pending apply only when active. Manual SyncNow requires the service that pause removed. Successful account SignOut retains the binding (`account/mod.rs:498–519`), while manual Resume/StartHost/Pair/CreateInvite still reject merely because the binding file exists (`adapter.rs:694–705`). Restart/relogin/repeated enable does not clear the durable inbox or provide its safe application route. Exit followed by manual Resume is therefore not an implemented escape hatch at this ref.

Two important limits: (1) aborted quiet is not itself proven permanently stuck: sync_tick recognizes abort and sync_release takes/removes the current operation (`session/synchronization.rs:468 onward,631 onward`); (2) actual conflict Resolve may start a local quiet operation even while inactive (`adapter.rs:820–888`). Neither supplies a general non-conflict inbox application action, and a conflict-only button can be absent or yield an empty list.

Required correction: retain the blocking checks and add a real, explicit handling route. A local-only pending-application operation may reuse the existing participant/editor/media validation while all transport stays stopped; missing media or invalid unprojected state needs a specific truthful prerequisite, preserving the retained data. Alternatively, a deliberately fenced post-logout restoration of the old manual session needs to be implemented, not merely described. Do not delete inbox/protocol data, automatically apply during login/status polling, or claim that “view conflicts” resolves every blocker. UI must distinguish conflict resolution from pending/unprojected data and transient save/quiet blocking. Core paused login may be accepted independently; enable recovery is not approved here.
