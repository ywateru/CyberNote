## P1 — offline retained-session recovery

Closed for the reported normal bound-session startup path. `retained_identity()` reads only an existing usable grant's previously accepted identity; it performs no request and returns no token. Startup presents this identity only when the current binding matches its subject and the pinned issuer. It does not take a profile from binding alone. The lifecycle generation is checked again inside the status mutation. Presented enabled intent is additionally gated by no adoption marker and an exact Store workspace/device; the presentation itself writes no enabled policy and starts no transport.

Thus a network error during refresh or the coordinator profile request retains a profile for the existing session, allowing main UI `accountConnectionRetry` to choose SyncNow. Native recovery still restores the grant and validates the remote profile before networking, and respects the persisted paused/enabled policy. SignIn now checks the retained grant before pause/set_enabled(false), preventing the incorrect retry from changing that policy. A failed fresh B authorization clears the presented profile as before; retained-session presentation runs only at startup and does not unconditionally resurrect old A from binding. Confirmed refresh rejection and cleanup remain distinct from ordinary network recovery.

The new AuthClient fixture checks zero requests from the local accessor, preserved grant bytes across a synthetic offline restore, Busy for a second authorization, and no identity returned for an unusable grant. The native helper checks both enabled values and mismatch rejection. These are inspected fixture assertions, not independently executed results or a complete Runtime/UI integration test.

## P2 — blocked adoption handling

Closed as a supported explicit recovery route, rather than automatic resolution of every blocker:

- Successful account SignOut first finishes auth logout, persists pause, remembers the current session as paused, then removes the current binding and adoption marker. It clears the in-memory binding only after private cleanup succeeds. The old business/protocol data, Noise credential and manual configuration are retained. A failed logout does not unblock manual transport prematurely.
- The old manual session can then Resume. Service setup validates its existing device before persisting opt-in. Missing manual credentials or a Store/device mismatch fail closed instead of creating a policy-free manual service over an account namespace.
- Returning to the old account requires a newly verified matching remote identity/profile/product/workspace, the DB's exact workspace/device, remembered/current matching session metadata and the existing matching Noise public key. A different subject, different device record or wrong key cannot borrow that namespace. Fresh login remains paused; the user must explicitly enable the original account space. Records remember enabled=false and contain no copied grant or private key.
- Manual Resume/SyncNow and verified account activation now initiate Session local recovery. Its dedicated purpose allows a nonempty projection-change plan when eligible inbox digests are empty. This closes both previous gates for a single unprojected head with inbox=0. It keeps the existing participant/probe/prepare, save-intent, Store/media authority and final-plan checks; it does not permit arbitrary workspace adoption or skip a protected editor.

Account activation treats the first recovery initiation as best effort. Busy/backoff, a missing participant, protected work, missing media or a failed event can defer that attempt. This is not another permanent enable dead end: after the old operation releases, manual SyncNow or the enabled old account's explicit SyncNow can initiate recovery again. Current UI says only that a request was sent and progress must be checked; it does not claim projection/application completion. The new head-only fixture inspects commit, ordinary-purpose rejection, blocked participant, changed participant, pending intent and empty-plan behavior. It does not establish actual user-window execution or event delivery.

Missing blob bytes cannot be manufactured offline. The help correctly requires returning to the legitimate old synchronization space with its original credential available, then explicitly enabling and handling its pending content. A missing/corrupt credential, unavailable old account or unavailable source bytes remains a real prerequisite; the code does not delete retained inbox/heads to conceal it. Conflict count zero is not interpreted as a clean adoption preflight. The updated UI exposes an explicit exit from error states and explains both manual and old-account recovery routes.
